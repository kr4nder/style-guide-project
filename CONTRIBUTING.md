# Как внести изменения в руководство

Спасибо, что помогаете улучшать руководство по стилю.
Документ описывает процесс от идеи до публикации.

## Как предложить изменение

1. Найдите или создайте Issue с описанием проблемы или идеи.
2. Создайте ветку от `main`. Имя ветки: `<тип>/<краткое-описание>`, например `docs/add-accessibility-section`.
3. Внесите изменения в файлы каталога `docs/`.
4. Проверьте текст линтером и локальной сборкой (см. ниже).
5. Сделайте коммит по правилам Conventional Commits.
6. Отправьте ветку на GitHub и создайте Pull Request в `main`.

Не вносите изменения напрямую в `main`.

## Требования к коммитам (Conventional Commits)

Формат сообщения:

```text
<тип>(<область>): <краткое описание>

<необязательное подробное описание>
```

Правила:

- Описание пишите в повелительном наклонении, со строчной буквы, без точки в конце.
- Длина первой строки — не более 72 символов.
- Область необязательна: `tone`, `spelling`, `formatting`, `markdown`, `doc-templates`, `glossary`, `ci`.

Допустимые типы:

| Тип | Когда использовать |
| --- | --- |
| `feat` | Новый раздел или новое правило |
| `fix` | Исправление ошибки в правиле или тексте |
| `docs` | Изменение служебной документации (README, CONTRIBUTING) |
| `style` | Форматирование без изменения смысла |
| `refactor` | Перестановка разделов без изменения правил |
| `ci` | Изменения в workflow GitHub Actions и настройках линтера |
| `chore` | Прочие технические изменения |

Примеры:

```text
feat(accessibility): add text accessibility rules
fix(spelling): correct date format example
ci: add markdownlint check to pull requests
```

## Процесс ревью

1. Автор создаёт Pull Request по шаблону и назначает ревьюера.
2. Автоматические проверки (линтер и сборка) должны пройти успешно.
3. Ревьюер оставляет комментарии: замечания, предложения, вопросы.
4. Автор вносит правки новыми коммитами в ту же ветку и отвечает на каждый комментарий.
5. Ревьюер проверяет правки и одобряет Pull Request (**Approve**).
6. Автор выполняет слияние в `main` (**Squash and merge** или **Merge**).
7. Автор убеждается, что изменения опубликованы на сайте.

Срок ответа ревьюера — три рабочих дня.

Ревьюер проверяет:

- соответствие текста правилам этого руководства;
- корректность примеров;
- работу навигации и ссылок;
- отсутствие ошибок линтера.

## Как запустить локальную сборку

Требуются Python 3.10 или новее и Node.js 18 или новее.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
mkdocs serve
```

На Windows активируйте окружение командой `.venv\Scripts\activate`.

Сайт будет доступен по адресу <http://127.0.0.1:8000> и обновится после сохранения файла.

Проверка перед созданием Pull Request:

```bash
npx markdownlint-cli2 "**/*.md"
mkdocs build --strict
```

## Как добавить новый раздел

1. Создайте файл в каталоге `docs/`. Имя — строчными латинскими буквами через дефис, например `docs/style/accessibility.md`.
2. Начните файл с заголовка первого уровня `#`.
3. Добавьте раздел в `nav` файла `mkdocs.yml`.
4. Проверьте ссылки: `mkdocs build --strict` не должен выдавать предупреждений.
5. Запустите линтер.
6. Создайте Pull Request.
